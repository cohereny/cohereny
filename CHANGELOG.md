# Changelog

What changed from one release of this repository to the next, written for people who run
Cohereny or build on it. Newest first. Auf Deutsch: [CHANGELOG.de.md](CHANGELOG.de.md).

Cohereny is pre-release. From 0.2.0 on, each release has a version number following
[Semantic Versioning](https://semver.org): before 1.0, a minor version (0.X.0) may change
behaviour incompatibly — the section says so —, a patch version (0.X.Y) only corrects. Each
release has a pre-release on GitHub tagged `vX.Y.Z`. The sections before 0.2.0 are snapshots
of the development repository, named after their date.

## 0.2.0 — 2026-11-12

### Added
- An `llm_call` node can carry an `output_schema`, a JSON Schema of type `object`. The model's answer is read as one JSON object — a single ```` ```json ```` block around it is accepted — checked, and added to the node's output as `data`, where edges (`data.risk_level`) and successors (`classify.data.risk_level`) read it. A mismatch fails the node and the run; the reason names where and which rule, never what the model wrote. The gateway is asked for JSON (`response_format`) for such a node ([guide](deploy/quickstart/guides/workflows.md#a-models-answer-as-data)).
- A `compute` node runs a calculation registered in the code, named by `function` and a pinned `function_version` — no code in the database, no expression language in a definition. Its result is the node's output as `data`. A missing figure, a value that is not a number or a denominator of 0 fails the step; a function the code does not have refuses the activation (`unknown_function`). Registered: `banking.ratios@1`, `banking.anomalies@1` ([guide](deploy/quickstart/guides/workflows.md#computed-steps)).
- A run can take documents — a PDF or a text file. A `document` node names one (`document_name`); a workflow with such nodes starts as `awaiting_documents`, and whoever started the run uploads each document with `PUT /v1/workflows/runs/{run_id}/documents/{name}`, the file as the body. The last one starts the run. A PDF is read to text when it arrives and the file is not kept; one without a text layer is refused. The text is scanned for instruction-shaped content — counted in the answer and the audit entry `workflow.run_document_received`, never quoted — and stored with the run's placeholders. Documents are not part of the run input: a step sees one only through an edge from its node. Limits: `DOCUMENT_MAX_BYTES` and `DOCUMENT_MAX_PAGES` for the installation (10 MB, 200 pages), lower ones per node; a node above the installation's refuses the activation (`document_limit_above_installation`) ([guide](deploy/quickstart/guides/workflows.md#documents)).
- `cc oversight expire` ends or escalates gates nobody decided, started by the operator's timer like `cc retention purge`. Past a gate's `review_timeout`, `on_timeout: reject` ends the run as `expired` — a new end state: nobody decided, neither a rejection nor a stop — and `on_timeout: escalate` hands it along a connection guarded by `{"op": "eq", "field": "decision", "value": "escalated"}` to a further gate. Activation refuses a time limit without an action and the reverse, an escalation without such a connection, one that leads anywhere but to a gate, and one to a gate that asks for fewer people. Audited as `workflow.run_expired` and `workflow.run_escalated`, without a person ([guide](deploy/quickstart/guides/workflows.md#reviews)).
- Areas at the gate (MaRisk BTO 1.1). A `human_review` node names its areas in `review_areas` — front office and back office, say — and each area casts one vote: all approve → released, all reject → `rejected`, the votes differ → escalated along the gate's escalation connection to a higher authority, which may be a single area of its own such as a credit committee. Areas are defined per scope and apply below it, kept by `admin` under `/v1/scopes/{scope_id}/review-areas`; removing a member revokes the membership with a date. The database refuses a vote without a current membership, a second vote for an area and one person for two areas. A vote names its area with `area` where its author belongs to several ([guide](deploy/quickstart/guides/workflows.md#areas)).
- A workflow carries a `risk_class` — `minimal`, `limited`, `high`. With the data class of its scope it sets the minimum of every gate: `limited` or `confidential` at least one approver, `high` or `critical` at least four eyes, two or more areas counting as four eyes. Activation refuses a gate below it (`review_below_minimum`). At run time the level is fixed when the run reaches a gate — the stricter of gate and minimum as they are then — and audited as `workflow.run_gate_reached` with what set it. After differing votes the higher authority decides as drawn; after a timeout it has to meet the minimum itself ([guide](deploy/quickstart/guides/workflows.md#how-strict-a-gate-must-be)).
- The review level `sample`. Where the scope's data class and the workflow's risk class are both lowest, a gate with `"review_role": "sample"` and `review_sample_rate` (0.001 to 1, at most three decimal places) lets the run go on and draws that share of its passes into a review queue — by a hash of the pass, so the draw recorded in `workflow.run_gate_reached` can be checked. `GET /v1/samples` lists what the caller may see, `GET /v1/samples/{sample_id}` shows one; `POST /v1/samples/{sample_id}/verdict` judges a pass once, from `reviewer` up, as `confirmed` or `objected`, audited as `workflow.sample_reviewed`. An objection recalls nothing; it is counted. Where the minimum asks for more, a sample gate waits as an approver gate ([guide](deploy/quickstart/guides/workflows.md#checked-afterwards)).
- A `context_compose` node can ask for blocks by tag: `"context_requirements": {"block_types": ["system_prompt"], "tags": ["banking:risiko"]}` composes only blocks that carry every tag named, on the version that would be composed. Each model step gets its own reviewed instruction instead of one context for the whole workflow ([guide](deploy/quickstart/guides/workflows.md#a-prompt-per-step)).
- A dotted target in `input_mapping` collects several values into one object (`"prompt.figures": "ratios.data"`), and an object as an `llm_call`'s prompt reaches the model in sections, a heading per key ([guide](deploy/quickstart/guides/workflows.md#several-inputs)).
- The credit analysis of the banking pilot as a workflow, in `deploy/examples/banking`: two documents, five model steps with a prompt each, two computed steps, the vote of front and back office with escalation to the credit committee. The bank statement reaches only the draft of the vote. `scripts/seed_banking_workflow.py` writes it through the API, everything as drafts ([README](deploy/examples/banking/README.md)).
- **An application log.** One JSON line per entry on stderr, the level set by `LOG_LEVEL` (default `INFO`). Each request has one line: request ID, method, route template, status, duration and, once known, the actor's UUID — never a value from the path, the query string, the client's address or any content. The server's own access line, which wrote the client's address and the full query string, is off. Every response carries `X-Request-ID`. Six places that passed over a failure in silence — a Redis that does not answer, among them — now write a warning. What the log holds and how long to keep it: [DATA-PROTECTION.md](DATA-PROTECTION.md) (item 5 of the checklist: 30 days recommended).
- **A model that answers 429 is skipped for a while.** The fallback chain already moved on after a 429, but asked the same model again on every request, so a used-up quota cost one refused round trip per call. Now the model is skipped for one minute, then five, fifteen and sixty after each further 429 in a row; a `Retry-After` from the gateway wins, up to an hour, and the model's first answer ends the streak. A skipped model appears as `skipped` in the attempts and so in `routing.fell_back`. The last candidate of a chain is always asked, so a chain of one behaves as before. The state is kept per stage in its Redis database; without Redis nothing is skipped.
- **The tested state between releases is public as the branch `next`.** After every deployment to the internal test stage that passes its checks, its state goes to GitHub `next`; `main` keeps the releases. A fix for a reported vulnerability carries the trailer `Embargo: CHY-…` and holds `next` until the release brings it to `main` ([SECURITY.md](SECURITY.md)).
- **Direct calls are spot-checked too.** Where `/v1/complete` answers, a share of its calls is drawn for a check afterwards: `minimal` now comes with `sample_rate` (0.001 to 1), the highest along the scope chain applies, and a scope classified `minimal` without one does not answer. A drawn call keeps what the model was asked and what it answered — placeholders where an identifier was replaced, never the value — and its block versions; the answer carries its `sample_id`. It waits in the same review queue as the passes of sample gates (`"source": "direct_call"`), visible to its caller, the scope's members and admin, judged once from `reviewer` up and audited as `direct_call.sample_reviewed`. Its content is cleared after the scope's content period, the row deleted after its trace period ([guide](deploy/quickstart/guides/scopes-and-blocks.md)).

### Changed
- **`/v1/complete` answers only where an answer may be used unchecked.** It has no gate, so it now answers only where the minimum review a gate would need is `sample`: data class `public` or `internal`, and direct calls in the scope classified `minimal`. Everywhere else it answers `409` with the reason, before any routing or model call — this includes every scope nobody classified, which counts as `high`. An architect classifies a scope with `PUT /v1/scopes/{id}/direct-call-risk-class` (`minimal` with a `sample_rate`, `limited`, `high`, or `null` to inherit); `GET` on the same path says whether direct calls answer there and why. Each setting is kept and audited; a scope may be stricter than the scopes above it, never looser. **After updating, classify the scopes in which you call `/v1/complete`, or use a workflow with a review gate.** The quickstart has a second scope, *Help Center*, where step 3 asks directly.
- **Releases have version numbers now.** This is 0.2.0, following Semantic Versioning: before 1.0, a minor version may change behaviour incompatibly — this one does (`/v1/complete`) —, a patch version only corrects. The version is in `pyproject.toml` alone and appears in the OpenAPI contract and in `/v1/health`. The setting `API_VERSION` is gone: an environment that still sets it is ignored, but a local `.env` *file* that contains it stops the API at start — remove the line. GitHub releases are tagged `vX.Y.Z`.
- **A workflow without a risk class counts as `high`, and a scope without a data class as `critical`: their gates ask for four eyes.** To classify an existing workflow, create it anew with a `risk_class`, release it and archive the old one. Versions of a workflow are planned. Runs already waiting at a gate keep the rule they reached it with. `risk_classification` is deprecated and read by nothing.
- **A high-risk workflow keeps its logs six months (AI Act Art. 26(6)).** Where a workflow classified `high` — or not classified, which counts as `high` — is active, neither the run trace nor the run content is kept for less than 183 days. Activating such a workflow is refused (`409`) while either period in its scope is shorter, and a change of a period that shortens it below six months there is refused too — set in the scope, further up the chain, or removed so a shorter one is inherited. Lengthening is always taken. **The shipped content period is 30 days: before activating a high-risk workflow, set `run_content` (and `run_trace`, if lowered) to at least 183 days in its scope** (`PUT /v1/admin/retention/{class}`). The banking example says so.
- A run that waits for documents counts for the retention periods like a finished one, from its creation: one whose documents never come is cleared with its period.
- A loop that runs out with no other way on — no `default` edge, nothing else running — ends the run as `failed`, naming the edge and its limit, instead of `complete`.
- In a direct scope (`project`, `sub_project`, `personal`) whoever may write may also take a block back and approve or reject one that waits — the `contributor` role, where a strict scope asks for `reviewer`. A contributor could make a block live there but not withdraw it. Approving a block that waits for a second person (a routing rule below `critical`, a loosened privacy rule) still needs a reviewer who did not write it.
- `scripts/seed_banking_workflow.py` writes through the API instead of SQL; it had stopped working with migration 023.
- The fixture PDFs of the banking pilot no longer print the expected risk class and anomalies.

### Fixed
- **A step with several inputs did not wait for them.** The graph a run is advanced on dropped each node's `join_policy`, so every join of a stored workflow behaved as `wait_any`: a `wait_all` step started on its first input and read the others as missing, and a `first_wins` step ran again for each straggler. Joins now behave as their definition says.
- **A loop that ran out of passes ended the run as `complete` — without the review after it.** A guarded edge back whose `loop_limit` was used up kept the `default` edge shut, nothing else was ready, and the run looked finished. An exhausted loop edge now counts as a condition that did not hold: the run goes on along the `default` edge, typically to the review. Each time a loop runs out, the audit log has an entry `workflow.loop_exhausted` (node, edge, limit, where the run went on to), and `GET /v1/workflows/runs/{run_id}/nodes` lists it under `exhausted_loops` — so whoever decides at the gate sees that the criterion was not met, only the budget spent ([guide](deploy/quickstart/guides/workflows.md#a-loop-that-runs-out)).
- A run nobody decided at its gate kept its content past every period; the purge leaves waiting runs alone. Once the content period of its scope has passed since it reached the gate, `cc oversight expire` ends it as `expired` and clears its content in the same step.
- `cc` failed in every container with "No module named 'cli'" — `cc retention purge` and `cc actor set-role` among the commands, and now `cc oversight expire`. The image installed the console script but not its packages. With the quickstart: `docker compose exec api cc oversight expire`.
- **The contract promised a list where a 422 can answer with a sentence.** FastAPI documents a 422 on every operation that takes input as a list of field errors. A rule that refuses a request answers with one sentence instead, and so does the refusal of a NUL character, which any text field can carry. A client generated from the contract failed to parse exactly the message it had to show. Every operation that takes input now documents `UnprocessableDetail`: `detail` is a list after failed validation and a sentence after a refusal. `HTTPValidationError` is no longer in the contract; a client that named that type uses `UnprocessableDetail`, whose list entries carry the same fields. The contract fuzzer now also checks the body of every documented answer against its schema.
- The workflow guide's branch example read `classify.content` — a path that never matched, because a condition reads the output of the node it starts from. It now reads `data.risk_level`.

### Security
- **An error from the model gateway told the caller where the gateway's model ran.** A 502 or 503 passed on the gateway's own text, which can name the private address and port of an inference host. An error that leaves the installation — an answer, a stored run, the audit log — now says what went wrong and ends with the request ID; what the gateway, the identity provider or a library said is in the application log under that ID. The same holds for a failed pilot run, which stored its whole traceback and sent the first 500 characters of it to the client. A run a person cancelled keeps its own message.
- **Token signing keys under 2048 bits are never used.** A token signed with a shorter RSA key from the identity provider's JWKS is refused with `503` and a request id — the identity provider has to rotate, not the caller —, and the application log names the key id and its length.
- **Vulnerabilities can also be reported through GitHub.** Besides security@cohereny.com, SECURITY.md now names GitHub's [private vulnerability reporting](https://github.com/cohereny/cohereny/security/advisories/new); both stay private, and the response times apply to both. `security.txt` on cohereny.com lists both, e-mail first.
- **A run's audit trail went to every reviewer, not only to those who see the run.** `GET /v1/audit-log?target=workflow_run:<id>` asked only for the role `reviewer`, so a reviewer of another scope read who started a run, who decided at its gate and who put its placeholders back, while the run itself answered 404. The same held for pilot runs and drawn direct calls. Now the audit trail of these three follows the object's visibility, and anyone else gets 404.
- **A technical account could decide at a workflow gate and judge a sample.** Only the role was checked, so an account in `chy-service-accounts` with `reviewer` or above could approve at a workflow gate and give the verdict on a drawn sample — including its own. Now it is refused with 403 and the decision stays open for a person, as it already was for data-flow blocks.


## 2026-11-08

### Added
- Workflow runs are stored with placeholders. Identifiers in a run's input, in every step's input and output and in the reasons given at a gate are replaced before they are stored; the mapping back to the values is encrypted per run under a key the database never sees. Whoever started a run, and from `reviewer` up whoever sees it, can have the values put back with `POST /v1/workflows/runs/{run_id}/resolve`, and every time is audited. The API needs `PII_MAPPING_KEYS` and does not start without it ([CRYPTOGRAPHY.md](CRYPTOGRAPHY.md)). Runs started before this update keep their values until their content period ends ([DATA-PROTECTION.md](DATA-PROTECTION.md)).
- Identifiers are replaced before every model call of `/v1/complete` and of a workflow: e-mail addresses, phone numbers, IBANs, German tax ids and health insurance numbers, labelled dates of birth, the values a caller lists in `identifiers_to_redact`, and a scope's own rules as reviewed `redaction_rule` blocks. The model, the gateway and the trace see placeholders; `/v1/complete` returns the answer with the values. A name nobody lists is not recognised yet.
- `POST /v1/workflows/runs/{run_id}/cancel` stops a run that has not finished (AI Act Art. 14(4)(e)), for whoever started it and, from `reviewer` up, whoever sees it. The run ends as `cancelled`, not as a rejection at the gate.
- Retention periods, installation-wide or per scope: `GET /v1/admin/retention`, `PUT /v1/admin/retention/{retention_class}`. `cc retention purge` clears a run's content when its period ends (default 30 days) and deletes its trace later (default 183 days). Run it on a schedule; nothing is deleted otherwise.
- Four eyes where data changes place: a routing rule that names a model below `critical`, and a block that loosens a privacy rule, are approved by someone who wrote nothing in that version. Accounts in the identity-provider group `chy-service-accounts` never approve them ([SECURITY.md](SECURITY.md)).
- For operators: [DATA-PROTECTION.md](DATA-PROTECTION.md), what Cohereny contributes to a data protection impact assessment, each measure with the test that shows it failing; a filled-in example for a hospital ([DATA-PROTECTION-EXAMPLE.md](DATA-PROTECTION-EXAMPLE.md), deutsch: [DATA-PROTECTION-EXAMPLE.de.md](DATA-PROTECTION-EXAMPLE.de.md)); and the cryptography concept ([CRYPTOGRAPHY.md](CRYPTOGRAPHY.md)).

### Changed
- Migrations only go forward. There are no down migrations; the way back from an update is the backup taken before it ([DEPENDENCIES.md](DEPENDENCIES.md)).
- The two LangGraph pilots, `/v1/pilots` and `/v1/questions`, are deprecated. Unlike a workflow they call the model with the values and store them; the API contract marks each of their operations `deprecated`. They are rebuilt as workflows on the runner. Until then, personal data belongs in workflows or `/v1/complete` ([DATA-PROTECTION.md](DATA-PROTECTION.md)).
- A quickstart updates with `git pull` and `docker compose up`: every start builds the image from the source, and the database keeps its data and is migrated. On a quickstart from 2026-11-04 the seed makes `reviewer` a member of Example Corp, without which `reviewer` would no longer see the runs (see Security) ([deploy/quickstart](deploy/quickstart/README.md#update)).

### Fixed
- A released workflow could be set back to `draft`, and its graph then changed underneath the runs that used it. That is refused with `409` now; a released workflow changes by a new version.
- A pilot run cancelled while it waited at its gate was booked as a rejection and stayed `running` without a result. It now ends as `failed`, with the cancellation as its message.

### Security
- Runs are readable only by whoever started them, by the members of the workflow's scope and of the scopes above, and by `admin`; row-level security enforces it in the database. Until now every signed-in user could read every run. Add the people who review runs to the scopes they work in (`POST /v1/scopes/{scope_id}/members`), or they no longer see them.
- The API runs with a database role of its own, `<database>_runtime`; `<database>_migrator` owns the tables and runs the migrations, and the API refuses to start as a superuser or an owner. Until now it could switch off the triggers that keep the audit log append-only. Existing installations create both roles once with `python -m migrations.roles` and point the API's `DATABASE_URL` at the runtime role ([DEPENDENCIES.md](DEPENDENCIES.md)).

## 2026-11-04

### Added
- A one-command quickstart in [deploy/quickstart](deploy/quickstart/): the API, a database, a cache, a local model (Ollama with `qwen2.5:1.5b`) and a development identity provider on one machine, with a worked example — scopes, blocks, routing rules and a workflow in which a model drafts a reply and a person approves it. A README and five guides; the walkthrough runs as a test on every change.
- `GET /v1/workflows/runs/{run_id}/nodes` shows what each node of a run produced. Whoever decides at a `human_review` gate can read the draft first; until now they decided without seeing it.
- `ROUTING_CONFIG` names the file that declares your models (`routing-config.yaml`). Until now that meant editing the file in the source tree.
- An `llm_call` node can take its system message through `input_mapping`, so a workflow hands a model the composed context and the run's input together, as `/v1/complete` does.
- `API_DOCS` serves `/docs`, `/redoc` and `/openapi.json` (off by default). `PILOT_NODE_METRICS` switches the banking pilot's token metrics.
- `scripts/dev_issuer.py`, a local stand-in for the identity provider in development and CI. It issues a token to anyone who asks; never run it where real data is.

### Changed
- Tokens are verified with PyJWT instead of python-jose. `exp`, `iss`, `aud` and `sub` are required; a token without one of them is refused.

### Removed
- `DEV_MODE`. If an `.env` still sets it, take it out: the API refuses to start with a key it does not know. To develop without an identity provider, use `scripts/dev_issuer.py` ([DEPENDENCIES.md](DEPENDENCIES.md)).

### Security
- No setting turns authentication off any more. Every route except `/v1/health` answers `401` without a token; a test walks all routes.
- The surface gate refuses a caller without a token audience instead of letting it through.
- An identity provider over plain `http://` is accepted only with `ENVIRONMENT=dev`.
