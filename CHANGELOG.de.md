# Changelog

Was sich von einer Ausgabe dieses Repositorys zur nächsten geändert hat, geschrieben für
alle, die Cohereny betreiben oder darauf aufbauen. Das Neueste zuerst. In English:
[CHANGELOG.md](CHANGELOG.md).

Cohereny ist ein Pre-Release. Ab 0.2.0 trägt jede Ausgabe eine Versionsnummer nach
[Semantic Versioning](https://semver.org): Vor 1.0 darf eine Minor-Version (0.X.0) Verhalten
inkompatibel ändern — der Abschnitt sagt es —, eine Patch-Version (0.X.Y) korrigiert nur. Jede
Ausgabe hat auf GitHub ein Pre-Release mit dem Tag `vX.Y.Z`. Die Abschnitte vor 0.2.0 sind
Schnappschüsse des Entwicklungs-Repositorys und heißen nach ihrem Datum.

## 0.2.0 — 2026-11-12

### Neu
- Ein `llm_call`-Knoten kann ein `output_schema` tragen, ein JSON Schema vom Typ `object`. Die Antwort des Modells wird als ein JSON-Objekt gelesen — ein einzelner ```` ```json ````-Block darum wird angenommen —, geprüft und als `data` in die Ausgabe des Knotens gelegt, wo Kanten (`data.risk_level`) und Nachfolger (`classify.data.risk_level`) es lesen. Eine Abweichung lässt Knoten und Lauf scheitern; die Begründung nennt Stelle und Regel, nie den Wert. Für einen solchen Knoten wird beim Gateway JSON angefordert (`response_format`) ([Anleitung](deploy/quickstart/guides/workflows.md#a-models-answer-as-data)).
- Ein `compute`-Knoten führt eine im Code registrierte Rechnung aus, benannt mit `function` und einer festen `function_version` — kein Code in der Datenbank, keine Ausdruckssprache in einer Definition. Das Ergebnis steht als `data` in der Ausgabe des Knotens. Eine fehlende Zahl, ein Wert, der keine Zahl ist, oder ein Nenner von 0 lässt den Schritt scheitern; eine Funktion, die der Code nicht kennt, verhindert die Aktivierung (`unknown_function`). Registriert: `banking.ratios@1`, `banking.anomalies@1` ([Anleitung](deploy/quickstart/guides/workflows.md#computed-steps)).
- Ein Lauf kann Dokumente bekommen — ein PDF oder eine Textdatei. Ein `document`-Knoten nennt eines (`document_name`); ein Workflow mit solchen Knoten startet als `awaiting_documents`, und wer den Lauf gestartet hat, lädt jedes Dokument mit `PUT /v1/workflows/runs/{run_id}/documents/{name}` hoch, die Datei als Body. Das letzte startet den Lauf. Ein PDF wird beim Eingang zu Text gelesen, die Datei nicht aufbewahrt; eines ohne Textebene wird abgelehnt. Der Text wird auf anweisungsförmige Inhalte geprüft — gezählt in der Antwort und im Audit-Eintrag `workflow.run_document_received`, nie zitiert — und mit den Platzhaltern des Laufs gespeichert. Dokumente gehören nicht zur Laufeingabe: Ein Schritt sieht eines nur über eine Kante von seinem Knoten. Grenzen: `DOCUMENT_MAX_BYTES` und `DOCUMENT_MAX_PAGES` für die Installation (10 MB, 200 Seiten), engere je Knoten; ein Knoten über der Installation verhindert die Aktivierung (`document_limit_above_installation`) ([Anleitung](deploy/quickstart/guides/workflows.md#documents)).
- `cc oversight expire` beendet oder eskaliert Gates, die niemand entschieden hat, angestoßen vom Timer des Betriebs wie `cc retention purge`. Ist das `review_timeout` eines Gates abgelaufen, beendet `on_timeout: reject` den Lauf als `expired` — ein neuer Endzustand: Niemand hat entschieden, es ist weder eine Ablehnung noch ein Abbruch —, und `on_timeout: escalate` gibt ihn über eine Verbindung mit der Bedingung `{"op": "eq", "field": "decision", "value": "escalated"}` an ein weiteres Gate. Die Aktivierung weist ein Zeitlimit ohne Aktion ab und umgekehrt, ebenso eine Eskalation ohne solche Verbindung, eine, die nicht zu einem Gate führt, und eine zu einem Gate, das weniger Personen verlangt. Im Audit als `workflow.run_expired` und `workflow.run_escalated`, ohne Person ([Anleitung](deploy/quickstart/guides/workflows.md#reviews)).
- Bereiche am Gate (MaRisk BTO 1.1). Ein `human_review`-Knoten nennt seine Bereiche in `review_areas`, etwa Markt und Marktfolge, und jeder Bereich gibt ein Votum ab: Alle stimmen zu → freigegeben, alle lehnen ab → `rejected`, die Voten weichen ab → eskaliert über die Eskalationsverbindung des Gates an eine höhere Stufe, auch an einen einzelnen eigenen Bereich wie eine Kreditkommission. Bereiche werden je Scope angelegt und gelten darunter, gepflegt von `admin` unter `/v1/scopes/{scope_id}/review-areas`; wer entfernt wird, verliert die Zugehörigkeit mit Datum. Die Datenbank weist ein Votum ohne aktuelle Zugehörigkeit ab, ein zweites Votum für einen Bereich und eine Person für zwei Bereiche. Wer zu mehreren Bereichen gehört, nennt seinen mit `area` ([Anleitung](deploy/quickstart/guides/workflows.md#areas)).
- Ein Workflow trägt eine `risk_class`, also `minimal`, `limited` oder `high`. Mit der Datenklasse seines Scopes setzt sie die Mindeststufe jedes Gates: Bei `limited` oder `confidential` ist es mindestens ein Approver, bei `high` oder `critical` mindestens vier Augen, und zwei oder mehr Bereiche zählen als vier Augen. Die Aktivierung weist ein Gate darunter ab (`review_below_minimum`). Zur Laufzeit wird die Stufe beim Erreichen des Gates festgehalten, als das Strengere aus Gate und Mindeststufe zu diesem Zeitpunkt, und als `workflow.run_gate_reached` mit ihrer Ursache auditiert. Nach abweichenden Voten entscheidet die höhere Stufe so, wie sie gezeichnet ist, nach einem Zeitablauf muss sie die Mindeststufe selbst erfüllen ([Anleitung](deploy/quickstart/guides/workflows.md#how-strict-a-gate-must-be)).
- Die Prüfstufe `sample`. Wo Datenklasse des Scopes und Risikoklasse des Workflows beide am niedrigsten sind, lässt ein Gate mit `"review_role": "sample"` und `review_sample_rate` (0,001 bis 1, höchstens drei Nachkommastellen) den Lauf weiterlaufen und zieht diesen Anteil der Durchläufe in eine Prüfwarteschlange. Gezogen wird über einen Hash des Durchlaufs, die in `workflow.run_gate_reached` vermerkte Ziehung lässt sich also nachprüfen. `GET /v1/samples` listet, was die Person sehen darf, `GET /v1/samples/{sample_id}` zeigt einen Eintrag. `POST /v1/samples/{sample_id}/verdict` beurteilt einen Durchlauf genau einmal, ab `reviewer`, als `confirmed` oder `objected`, und wird als `workflow.sample_reviewed` auditiert. Eine Beanstandung holt nichts zurück, sie wird gezählt. Verlangt die Mindeststufe mehr, wartet ein `sample`-Gate wie ein Approver-Gate ([Anleitung](deploy/quickstart/guides/workflows.md#checked-afterwards)).
- Ein `context_compose`-Knoten kann Blöcke nach Tag anfordern: `"context_requirements": {"block_types": ["system_prompt"], "tags": ["banking:risiko"]}` komponiert nur Blöcke, die jedes genannte Tag tragen, und zwar an der Version, die komponiert würde. Jeder Modellschritt bekommt so seine eigene geprüfte Anweisung statt eines Kontexts für den ganzen Workflow ([Anleitung](deploy/quickstart/guides/workflows.md#a-prompt-per-step)).
- Ein Ziel mit Punkt in `input_mapping` sammelt mehrere Werte in einem Objekt (`"prompt.figures": "ratios.data"`). Ein Objekt als Prompt eines `llm_call` erreicht das Modell in Abschnitten, eine Überschrift je Schlüssel ([Anleitung](deploy/quickstart/guides/workflows.md#several-inputs)).
- Die Kreditanalyse des Banking-Piloten als Workflow, in `deploy/examples/banking`: zwei Dokumente, fünf Modellschritte mit je eigenem Prompt, zwei Rechenschritte, das Votum von Markt und Marktfolge mit Eskalation an die Kreditkommission. Der Kontoauszug erreicht nur den Entwurf des Votums. `scripts/seed_banking_workflow.py` legt alles über die API an, jeweils als Entwurf ([README](deploy/examples/banking/README.md)).
- **Ein Anwendungslog.** Eine JSON-Zeile je Eintrag auf stderr, die Stufe über `LOG_LEVEL` (Vorgabe `INFO`). Je Request eine Zeile mit Request-ID, Methode, Routen-Schablone, Status, Dauer und, sobald bekannt, der UUID des Akteurs. Nie darin: ein Wert aus dem Pfad, der Query-String, die Adresse des Clients oder irgendein Inhalt. Die eigene Zugriffszeile des Servers, die Client-Adresse und vollen Query-String schrieb, ist abgeschaltet. Jede Antwort trägt `X-Request-ID`. Sechs Stellen, die einen Fehler stillschweigend übergingen, schreiben jetzt eine Warnung, darunter ein Redis, das nicht antwortet. Was das Log enthält und wie lange man es aufbewahrt, steht in [DATA-PROTECTION.md](DATA-PROTECTION.md) (Punkt 5 der Checkliste: 30 Tage empfohlen).
- **Ein Modell, das 429 meldet, wird eine Zeit lang übersprungen.** Die Ausweichkette schaltete nach einem 429 schon weiter, fragte dasselbe Modell aber bei jeder Anfrage erneut. Eine erschöpfte Quote kostete so je Aufruf einen abgelehnten Umlauf. Jetzt wird das Modell übersprungen, eine Minute lang, nach jedem weiteren 429 in Folge fünf, fünfzehn und sechzig Minuten. Ein `Retry-After` des Gateways hat Vorrang, höchstens eine Stunde, und die erste Antwort des Modells beendet die Folge. Ein übersprungenes Modell steht als `skipped` in den Versuchen und damit in `routing.fell_back`. Der letzte Kandidat einer Kette wird immer gefragt, eine Kette mit einem Modell verhält sich also wie bisher. Der Zustand liegt je Stufe in deren Redis-Datenbank; ohne Redis wird nichts übersprungen.
- **Der getestete Stand zwischen den Releases ist öffentlich, als Branch `next`.** Nach jedem Deploy auf die interne Teststufe, der seine Prüfungen besteht, geht ihr Stand nach GitHub `next`; `main` behält die Releases. Eine Korrektur für eine gemeldete Lücke trägt die Zeile `Embargo: CHY-…` und hält `next` an, bis der Release sie nach `main` bringt ([SECURITY.md](SECURITY.md)).
- **Auch direkte Aufrufe werden stichprobenartig geprüft.** Wo `/v1/complete` antwortet, wird ein Anteil der Aufrufe für eine Prüfung im Nachhinein gezogen: Zu `minimal` gehört jetzt `sample_rate` (0,001 bis 1), entlang der Bereichskette gilt der höchste Anteil, und ein Bereich mit `minimal` ohne Anteil antwortet nicht. Ein gezogener Aufruf behält, was das Modell gefragt wurde und was es antwortete — Platzhalter, wo eine Kennung ersetzt wurde, nie den Wert — und seine Blockversionen; die Antwort nennt seine `sample_id`. Er wartet in derselben Prüfwarteschlange wie die Durchläufe der Stichproben-Gates (`"source": "direct_call"`), sichtbar für den Aufrufer, die Mitglieder des Bereichs und `admin`, wird genau einmal ab `reviewer` beurteilt und als `direct_call.sample_reviewed` auditiert. Der Inhalt wird nach der Inhaltsfrist des Bereichs geleert, die Zeile nach seiner Spurfrist gelöscht ([Anleitung](deploy/quickstart/guides/scopes-and-blocks.md)).

### Geändert
- **`/v1/complete` antwortet nur noch, wo eine Antwort ungeprüft genutzt werden darf.** Der Endpunkt hat kein Gate und antwortet deshalb nur, wo die Mindeststufe, die ein Gate bräuchte, `sample` ist: Datenklasse `public` oder `internal`, und direkte Aufrufe im Bereich als `minimal` eingestuft. Überall sonst kommt `409` mit dem Grund, vor jedem Routing und jedem Modellaufruf. Das gilt auch für jeden Bereich, den niemand eingestuft hat; er zählt als `high`. Einstufen kann ab `architect`: `PUT /v1/scopes/{id}/direct-call-risk-class` (`minimal` mit `sample_rate`, `limited`, `high` oder `null`, um zu erben); `GET` auf denselben Pfad sagt, ob direkte Aufrufe dort antworten und warum. Jede Einstufung bleibt erhalten und steht im Audit; ein Bereich darf strenger sein als die darüber, nie lockerer. **Nach dem Update die Bereiche einstufen, in denen `/v1/complete` aufgerufen wird, oder einen Workflow mit Gate nehmen.** Der Quickstart hat dafür einen zweiten Bereich, *Help Center*, in dem Schritt 3 direkt fragt.
- **Ausgaben tragen jetzt Versionsnummern.** Dies ist 0.2.0, nach Semantic Versioning: Vor 1.0 darf eine Minor-Version Verhalten inkompatibel ändern — diese tut es (`/v1/complete`) —, eine Patch-Version korrigiert nur. Die Version steht allein in `pyproject.toml` und erscheint im OpenAPI-Vertrag und in `/v1/health`. Die Einstellung `API_VERSION` entfällt: Eine Umgebung, die sie noch setzt, wird ignoriert; eine lokale `.env`-*Datei* mit dieser Zeile hält die API beim Start an — die Zeile löschen. GitHub-Releases heißen `vX.Y.Z`.
- **Ein Workflow ohne Risikoklasse zählt als `high`, ein Scope ohne Datenklasse als `critical`. Ihre Gates verlangen dann vier Augen.** Um einen bestehenden Workflow einzustufen, legt man ihn mit einer `risk_class` neu an, gibt ihn frei und archiviert den alten. Versionen eines Workflows sind geplant. Läufe, die schon an einem Gate warten, behalten die Regel, mit der sie es erreicht haben. `risk_classification` ist abgekündigt und wird von nichts gelesen.
- **Ein Hochrisiko-Workflow hält seine Protokolle sechs Monate (KI-VO Art. 26(6)).** Wo ein Workflow mit `high` — oder ohne Einstufung, die als `high` zählt — aktiv ist, fällt weder die Laufspur noch der Laufinhalt unter 183 Tage. Einen solchen Workflow zu aktivieren wird abgelehnt (`409`), solange eine der Fristen in seinem Bereich kürzer ist, und eine Änderung, die eine Frist dort unter sechs Monate verkürzt, ebenso — im Bereich gesetzt, weiter oben in der Kette oder durch Entfernen, das eine kürzere erben lässt. Verlängern geht immer. **Die ausgelieferte Inhaltsfrist ist 30 Tage: vor dem Aktivieren eines Hochrisiko-Workflows `run_content` (und `run_trace`, falls gesenkt) in seinem Bereich auf mindestens 183 Tage setzen** (`PUT /v1/admin/retention/{class}`). Das Banking-Beispiel sagt es.
- Ein Lauf, der auf Dokumente wartet, zählt für die Aufbewahrungsfristen wie ein beendeter, ab seiner Anlage: Einer, dessen Dokumente nie kommen, wird mit seiner Frist geleert.
- Eine Schleife, die ohne anderen Weg ausläuft — keine `default`-Kante, sonst läuft nichts —, beendet den Lauf als `failed` und nennt Kante und Grenze, statt als `complete`.
- In einem direkten Bereich (`project`, `sub_project`, `personal`) darf, wer dort schreiben darf, einen Block auch zurückziehen und einen wartenden freigeben oder ablehnen. Dafür genügt die Rolle `contributor`, wo ein strenger Bereich `reviewer` verlangt. Bisher konnte ein Contributor einen Block dort live schalten, aber nicht wieder abschalten. Einen Block freizugeben, der auf eine zweite Person wartet (eine Routing-Regel unterhalb von `critical`, eine gelockerte Datenschutzregel), verlangt weiter einen Reviewer, der ihn nicht geschrieben hat.
- `scripts/seed_banking_workflow.py` schreibt über die API statt per SQL; seit Migration 023 lief es nicht mehr.
- Die Fixture-PDFs des Banking-Piloten drucken die erwartete Risikoklasse und die erwarteten Auffälligkeiten nicht mehr.

### Behoben
- **Ein Schritt mit mehreren Eingängen wartete nicht auf sie.** Der Graph, auf dem ein Lauf vorrückt, ließ die `join_policy` jedes Knotens weg. Damit verhielt sich jede Zusammenführung eines gespeicherten Workflows wie `wait_any`: Ein `wait_all`-Schritt startete mit seinem ersten Eingang und las die übrigen als fehlend, ein `first_wins`-Schritt lief für jeden Nachzügler erneut. Zusammenführungen verhalten sich jetzt so, wie ihre Definition sagt.
- **Eine Schleife, die ihre Durchläufe aufgebraucht hatte, beendete den Lauf als `complete`, ohne die Prüfung danach.** Ein bewachter Rücksprung mit aufgebrauchtem `loop_limit` hielt die `default`-Kante geschlossen, sonst war nichts bereit, und der Lauf sah fertig aus. Eine erschöpfte Schleifenkante zählt jetzt wie eine Bedingung, die nicht gegriffen hat: Der Lauf geht über die `default`-Kante weiter, in der Regel zur Prüfung. Jede erschöpfte Schleife steht im Audit-Log als `workflow.loop_exhausted` (Knoten, Kante, Grenze, wohin der Lauf weiterging), und `GET /v1/workflows/runs/{run_id}/nodes` führt sie unter `exhausted_loops`. Wer am Gate entscheidet, sieht damit, dass das Kriterium nicht erfüllt, sondern nur das Budget aufgebraucht ist ([Anleitung](deploy/quickstart/guides/workflows.md#a-loop-that-runs-out)).
- Ein Lauf, den niemand am Gate entschied, behielt seinen Inhalt über jede Frist hinaus, denn das Löschen lässt wartende Läufe in Ruhe. Ist die Inhaltsfrist seines Bereichs seit Erreichen des Gates abgelaufen, beendet `cc oversight expire` ihn als `expired` und leert seinen Inhalt im selben Schritt.
- `cc` scheiterte in jedem Container mit „No module named 'cli'“, darunter `cc retention purge` und `cc actor set-role`, jetzt auch `cc oversight expire`. Das Image installierte den Befehl, aber nicht seine Pakete. Mit dem Quickstart: `docker compose exec api cc oversight expire`.
- **Der Vertrag versprach eine Liste, wo eine 422 mit einem Satz antworten kann.** FastAPI dokumentiert die 422 jeder Operation mit Eingabe als Liste von Feldfehlern. Eine Regel, die eine Anfrage ablehnt, antwortet aber mit einem Satz, ebenso die Ablehnung eines NUL-Zeichens, das in jedem Textfeld stehen kann. Ein aus dem Vertrag erzeugter Client scheiterte genau an der Meldung, die er zeigen müsste. Jede Operation mit Eingabe dokumentiert jetzt `UnprocessableDetail`: `detail` ist nach gescheiterter Validierung eine Liste, nach einer Ablehnung ein Satz. `HTTPValidationError` steht nicht mehr im Vertrag. Ein Client, der diesen Typ benannt hat, nimmt `UnprocessableDetail`, dessen Listeneinträge dieselben Felder tragen. Der Vertrags-Fuzzer prüft jetzt zusätzlich den Körper jeder dokumentierten Antwort gegen ihr Schema.
- Das Beispiel für Verzweigungen im Workflow-Guide las `classify.content` — ein Pfad, der nie traf, denn eine Bedingung liest die Ausgabe des Knotens, von dem sie ausgeht. Es liest jetzt `data.risk_level`.

### Sicherheit
- **Ein Fehler des Modell-Gateways verriet dem Aufrufer, wo dessen Modell lief.** Ein 502 oder 503 reichte den Text des Gateways weiter, und der kann Adresse und Port eines internen Inferenz-Rechners nennen. Ein Fehler, der die Installation verlässt, ob als Antwort, im gespeicherten Lauf oder im Audit-Log, sagt jetzt, was schiefging, und endet mit der Request-ID. Was Gateway, Identity Provider oder eine Bibliothek dazu geschrieben haben, steht unter dieser ID im Anwendungslog. Dasselbe gilt für einen gescheiterten Pilotlauf: Er speicherte bisher seinen ganzen Traceback und schickte dem Client die ersten 500 Zeichen davon. Ein Lauf, den eine Person abgebrochen hat, behält seine eigene Meldung.
- **Signierschlüssel unter 2048 Bit werden nie benutzt.** Ein Token, das mit einem kürzeren RSA-Schlüssel aus dem JWKS des Identitätsanbieters signiert ist, wird mit `503` und Request-ID abgewiesen — rotieren muss der Identitätsanbieter, nicht der Aufrufer —, und das Anwendungslog nennt Schlüssel-ID und Länge.
- **Sicherheitslücken lassen sich auch über GitHub melden.** Neben security@cohereny.com nennt SECURITY.md jetzt GitHubs [Private vulnerability reporting](https://github.com/cohereny/cohereny/security/advisories/new). Beide Wege bleiben vertraulich, die Reaktionszeiten gelten für beide. Die `security.txt` von cohereny.com nennt beide, die E-Mail zuerst.
- **Der Audit-Trail eines Laufs ging an jeden `reviewer`, nicht nur an die, die den Lauf sehen.** `GET /v1/audit-log?target=workflow_run:<id>` verlangte nur die Rolle `reviewer`. Ein Prüfer aus einem fremden Bereich las so, wer einen Lauf startete, wer an seinem Gate entschied und wer seine Platzhalter auflöste, während der Lauf selbst 404 antwortete. Dasselbe galt für Pilotläufe und gezogene direkte Aufrufe. Jetzt folgt der Audit-Trail dieser drei der Sichtbarkeit des Objekts, alle anderen bekommen 404.
- **Ein technisches Konto konnte an einem Workflow-Gate entscheiden und über Stichproben urteilen.** Geprüft wurde nur die Rolle. Ein Konto in `chy-service-accounts` mit `reviewer` oder höher konnte an einem Workflow-Gate freigeben und das Urteil über eine gezogene Stichprobe abgeben, auch über die eigene. Jetzt wird es mit 403 abgewiesen, und die Entscheidung bleibt offen für eine Person, wie es für Datenfluss-Blöcke schon galt.


## 2026-11-08

### Neu
- Workflow-Läufe werden mit Platzhaltern gespeichert. Bezeichner in der Eingabe eines Laufs, in Ein- und Ausgabe jedes Schritts und in den Begründungen am Gate werden ersetzt, bevor sie gespeichert werden; die Zuordnung zu den Werten ist je Lauf verschlüsselt, mit einem Schlüssel, den die Datenbank nie sieht. Wer den Lauf gestartet hat, und ab `reviewer` jeder, der ihn sieht, kann sich die Werte mit `POST /v1/workflows/runs/{run_id}/resolve` zurückholen, jedes Mal protokolliert. Die API braucht `PII_MAPPING_KEYS` und startet ohne nicht ([CRYPTOGRAPHY.md](CRYPTOGRAPHY.md)). Läufe, die vor diesem Update gestartet wurden, behalten ihre Werte, bis ihre Inhaltsfrist abläuft ([DATA-PROTECTION.md](DATA-PROTECTION.md)).
- Bezeichner werden vor jedem Modellaufruf von `/v1/complete` und in Workflows ersetzt: E-Mail-Adressen, Telefonnummern, IBANs, Steuer-IDs und Krankenversichertennummern, gekennzeichnete Geburtsdaten, die Werte, die ein Aufrufer in `identifiers_to_redact` nennt, und die eigenen Regeln eines Bereichs als geprüfte `redaction_rule`-Blöcke. Modell, Gateway und Trace sehen Platzhalter; `/v1/complete` liefert die Antwort mit den Werten. Einen Namen, den niemand nennt, erkennt Cohereny noch nicht.
- `POST /v1/workflows/runs/{run_id}/cancel` hält einen Lauf an, der noch nicht beendet ist (KI-Verordnung Art. 14(4)(e)) — für die Person, die ihn gestartet hat, und ab `reviewer` für alle, die ihn sehen. Der Lauf endet als `cancelled`, nicht als Ablehnung am Gate.
- Aufbewahrungsfristen für die ganze Installation oder je Bereich: `GET /v1/admin/retention`, `PUT /v1/admin/retention/{retention_class}`. `cc retention purge` leert die Inhalte eines Laufs, wenn ihre Frist abläuft (Vorgabe 30 Tage), und löscht seine Spur später (Vorgabe 183 Tage). Regelmäßig ausführen, sonst wird nichts gelöscht.
- Vier Augen, wo Daten den Ort wechseln: Eine Routing-Regel, die ein Modell unterhalb von `critical` nennt, und ein Block, der eine Datenschutzregel lockert, gibt jemand frei, der an dieser Version nichts geschrieben hat. Konten in der Gruppe `chy-service-accounts` des Identity Providers geben sie nie frei ([SECURITY.md](SECURITY.md)).
- Für Betreiber: [DATA-PROTECTION.md](DATA-PROTECTION.md), was Cohereny zu einer Datenschutz-Folgenabschätzung beiträgt, jede Maßnahme mit dem Test, der fällt, wenn man sie entfernt; ein ausgefülltes Beispiel für eine Klinik ([DATA-PROTECTION-EXAMPLE.de.md](DATA-PROTECTION-EXAMPLE.de.md), englisch: [DATA-PROTECTION-EXAMPLE.md](DATA-PROTECTION-EXAMPLE.md)); und das Kryptokonzept ([CRYPTOGRAPHY.md](CRYPTOGRAPHY.md)).

### Geändert
- Migrationen gehen nur vorwärts. Es gibt keine Rückwärtsmigrationen; der Weg zurück aus einem Update ist das Backup davor ([DEPENDENCIES.md](DEPENDENCIES.md)).
- Die beiden LangGraph-Piloten, `/v1/pilots` und `/v1/questions`, sind abgekündigt. Anders als ein Workflow rufen sie das Modell mit den Werten auf und speichern sie; der API-Vertrag kennzeichnet jede ihrer Operationen als `deprecated`. Sie werden als Workflows auf den Runner umgestellt. Bis dahin gehören Personendaten in Workflows oder `/v1/complete` ([DATA-PROTECTION.md](DATA-PROTECTION.md)).
- Einen Schnellstart aktualisieren `git pull` und `docker compose up`: Jeder Start baut das Image aus dem Quellcode, die Datenbank behält ihre Daten und wird migriert. Bei einem Schnellstart vom 2026-11-04 trägt der Seed `reviewer` als Mitglied von Example Corp ein; ohne das sähe `reviewer` die Läufe nicht mehr (siehe Sicherheit) ([deploy/quickstart](deploy/quickstart/README.md#update)).

### Behoben
- Ein freigegebener Workflow ließ sich auf `draft` zurücksetzen, und sein Graph war dann änderbar, unter den Läufen, die ihn benutzt hatten. Das wird jetzt mit `409` abgewiesen; ein freigegebener Workflow ändert sich über eine neue Version.
- Ein Pilotlauf, der am Gate wartete und abgebrochen wurde, wurde als Ablehnung verbucht und blieb ohne Ergebnis auf `running`. Er endet jetzt als `failed`, mit dem Abbruch als Meldung.

### Sicherheit
- Läufe lesen nur, wer sie gestartet hat, die Mitglieder des Workflow-Bereichs und der Bereiche darüber und `admin`; Row-Level Security setzt das in der Datenbank durch. Bisher las jede angemeldete Person jeden Lauf. Wer Läufe prüft, muss Mitglied der Bereiche sein, in denen sie entstehen (`POST /v1/scopes/{scope_id}/members`), sonst bleiben sie verborgen.
- Die API läuft mit einer eigenen Datenbankrolle, `<database>_runtime`; `<database>_migrator` besitzt die Tabellen und führt die Migrationen aus, und als Superuser oder Eigentümerin startet die API nicht. Bisher konnte sie die Trigger abschalten, die das Audit-Log nur anfügbar halten. Bestehende Installationen legen beide Rollen einmal mit `python -m migrations.roles` an und richten `DATABASE_URL` der API auf die Laufzeitrolle ([DEPENDENCIES.md](DEPENDENCIES.md)).

- Tokens prüft PyJWT statt python-jose. `exp`, `iss`, `aud` und `sub` sind Pflicht; ein Token, dem eines davon fehlt, wird abgewiesen.

### Entfernt
- `DEV_MODE`. Steht er noch in einer `.env`, muss er heraus: Die API startet nicht mit einem Schlüssel, den sie nicht kennt. Für die Entwicklung ohne Identity Provider gibt es `scripts/dev_issuer.py` ([DEPENDENCIES.md](DEPENDENCIES.md)).

- Kein Schalter schaltet die Authentifizierung mehr ab. Jede Route außer `/v1/health` antwortet ohne Token mit `401`; ein Test geht alle Routen durch.
